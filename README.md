# work-hub

> 把异构 AI 客户端当成可替换的工人，用**工单契约 + 硬闸验收 + 分层裁决**来管的本地调度器。

不是又一个模型网关，不是又一块 agent 看板，也不是又一个 agent 框架。

---

## 它解决什么问题

你手上同时装着 CLI agent、IDE 插件、桌面 AI 应用。它们各自有登录态、各自的模型、各自的工作目录，互相不知道对方存在。

结果：

- 同一个任务，你只能手动挑一个客户端干，没法让三个同时干再比结果
- 干完了，好不好全靠你自己看，没有可执行的验收标准
- 两个客户端给出相反结论时，你不知道该信谁
- 换一个客户端，之前积累的用法全部作废

work-hub 把这三件事拆开管：**派给谁**（路由）、**干得对不对**（契约验收）、**谁说了算**（分层裁决）。

---

## 核心能力

| #   | 能力            | 说明                                                                 |
| --- | ------------- | ------------------------------------------------------------------ |
| 1   | **异构客户端接入**   | 同一份工单可派给 CLI / IDE 插件 / Electron 桌面端，按客户端类型自动选 ACP / CDP / 子进程三种通道 |
| 2   | **任务路由**      | 一句话判断该走哪个环节、用哪张技能卡                                                 |
| 3   | **派单 + 契约验收** | 派出去的不是"帮我做一下"，是带 schema 的工单；回收后按契约逐项判定，不合格打回                       |
| 4   | **分层裁决**      | 多个评审者打分不一致时，按层级升级裁决，而不是简单取平均                                       |
| 5   | **能力测量**      | 同一任务、同一技能卡、跨客户端跑，记录 request / response / 耗时 / 成功率，产出对比             |
| 6   | **技能卡**       | 把"某类任务怎么做"写成可执行卡片，带格式校验与硬闸（不合格不许进下一阶段）                             |

**明确不做**：不做模型网关（协议转换交给 LiteLLM 一类）、不做 MCP server 聚合、不做聊天 UI、不做 tmux 多开。

## 架构

```
┌──────────────────────────────────────────────────────────────┐
│  客户端层（别人的二进制）                                      │
│  CLI agent        IDE 插件        Electron 桌面应用           │
└───────┬──────────────┬──────────────────┬────────────────────┘
        │ ACP          │ 子进程 / 结构化输出 │ CDP
┌───────▼──────────────▼──────────────────▼────────────────────┐
│  适配层  adapter × N   统一成 { send(task) -> result }        │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│  调度层                                                       │
│  Router ──▶ Dispatch ──▶ Verdict（契约） ──▶ Judge（分层裁决） │
│                │                              │               │
│                └──────── 不合格则打回 ◀────────┘               │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│  观测层  Measure（跨客户端跑分） · RunIndex（工单轨迹）        │
└──────────────────────────────────────────────────────────────┘
```

## 和其他项目的区别

| 项目                                                                     | Star  | 它做什么                            | 与 work-hub 的关系                                                     |
| ---------------------------------------------------------------------- | ----- | ------------------------------- | ------------------------------------------------------------------ |
| [claude-code-router](https://github.com/musistudio/claude-code-router) | 38.1k | 把各客户端的 **API 流量**改道到任意 provider | 它管请求，我管交付。我不改道，我派单、验收、打回                                           |
| [vibe-kanban](https://github.com/BloopAI/vibe-kanban)                  | 28.6k | 看板式派单，**人**审 diff               | 它是给人看的看板，我是给机器判的门。人可以不在场                                           |
| [LangGraph](https://github.com/langchain-ai/langgraph)                 | 44.8k | 编排**你自己写的** agent 对象            | LangGraph 编排 agent，我编排客户端。它假设 agent 是 Python 对象，我假设 agent 是别人家的二进制 |
| [LiteLLM](https://github.com/BerriAI/litellm)                          | 63.1k | API 层统一协议、路由、计费                 | 我在客户端层，在它上面；可以内置它，不替代它                                             |

**一句话差异**：别人做的是"让请求到达模型"，我做的是"让任务到达工人，并判定工人干得对不对"。

## 命名与术语

- **工单（ticket）**：一次派单的完整输入输出记录
- **契约（contract）**：验收标准的机器可读描述
- **硬闸（gate）**：不满足契约就阻断流转，不是警告
- **技能卡（skill card）**：一个环节的可执行做法说明
